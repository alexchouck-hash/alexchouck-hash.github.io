How it works

  1. CAD-01

    Pick the pilot set

    A representative assembly — ideally your ugliest one. Complex features, imported bodies, and legacy history are what stress the method, and that is what a pilot is for.

  2. CAD-02

    Migrate

    Geometry and metadata are converted to the target platform with the assembly structure and configuration intent preserved where the target supports it.

  3. CAD-03

    Check and sign

    Automated comparison against the source: geometric deviation, mass properties, feature and constraint integrity, drawing references, PDM metadata. Deviations are listed, not smoothed over. A named engineer signs each model.

  4. CAD-04

    Report and decide

    You get the migrated set, the verification report, and a per-model estimate for the full library — enough to decide whether to run the whole migration at all.

Questions we get

Which platforms do you support?

Supported source and target platforms are listed in the pilot one-pager. If your pairing is not on it, tell us — the honest answer is sometimes that the pairing needs a feasibility check before we would quote a pilot at all.

How is fidelity actually verified?

By comparison against the source model, not by eyeballing the result: geometric deviation against a stated tolerance, mass and volume properties, feature and constraint integrity, and metadata carry-over. Each check has a pass criterion written down before the migration runs, and each result is signed by a named engineer.

What happens to drawings?

Models and drawings are treated as separate problems, because they are. Model migration is the primary deliverable; drawing handling — regeneration, reference repair, or deliberate re-creation — is scoped explicitly in the pilot so nobody discovers at the end that the views detached. The pilot report states exactly what happened to every drawing in the set.

Does PDM or PLM metadata come across?

Metadata carry-over is part of the check suite: part numbers, revisions, descriptions, custom properties, and configuration data are mapped to the target’s schema and verified per model. Where the target has no equivalent field, that is reported as a mapping gap rather than silently dropped.

Why start with a pilot set instead of the whole library?

Because migration quality is a property of your specific geometry and modelling history, and no vendor can honestly promise a number before seeing it. A pilot converts an unbounded project into a fixed-price test with a report at the end, and gives both sides a per-model estimate grounded in your actual models.

Is the migrated data usable in a regulated file?

That is your quality system’s call, which is why the pilot produces a verification report rather than just files. The report is built to be filed as objective evidence that the migration was checked, against stated criteria, by a named reviewer.
